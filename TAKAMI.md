# Takami: как это устроено

Основание: разбор AniLabX 5.8, Tadami, Aniyomi и полугодовая работа над
[extension-forge](https://github.com/ilyuzorpyramur-glitch/extension-forge), где тот же
генератор живёт на компьютере и собирает APK.

## Идея в одном абзаце

Takami — форк Tadami, который умеет **создавать источники внутри себя**: пользователь
вставляет ссылку на сайт, приложение разбирает вёрстку, собирает описание источника,
само себя проверяет и регистрирует источник так, что он **неотличим от APK-расширения**
(иконка, название, версия, настройки, список источников). В приложении нет ни одного
знания о конкретных сайтах — только движок и локальные профили, выученные на устройстве.

## Почему генератор в приложении, а не APK на каждый сайт

| Вариант | Проблема |
|---|---|
| APK на каждый сайт | CI, подпись, `extVersionCode`, index.json, установка — 15 минут на правку |
| Спеки с сервера | знание о сайтах централизовано у одного человека: единая точка отказа |
| **Генератор в приложении** | **знания о сайте возникают у пользователя и остаются у него** |

Юридически это самая чистая конфигурация: приложение — браузер с библиотекой и
генератором, сайты в него не вшиты, источники создаёт сам пользователь.

## Что берём из апстрима, а что пишем сами

Tadami (`andarcanum/Tadami-Aniyomi-fork`) под **Apache-2.0**, поэтому синхронизация
кода законна при сохранении `LICENSE` и уведомления об изменениях. Апстрим даёт:
плеер, читалку, библиотеку, историю, загрузки, трекинг (Shikimori/MAL/AniList),
бэкапы, миграцию, APK-расширения и их репозитории.

Пишем сами: спецификацию источника, интерпретатор, генератор, самопроверку, профили
сайтов и экраны «Добавить по ссылке».

## Генератор — не LLM на устройстве

Локальная модель на телефоне не потянет разбор вёрстки. Реалистичная схема — три ступени:

| Ступень | Что делает | Стоимость |
|---|---|---|
| 1. Детерминированная | определяет движок (DLE, WordPress, JSON API, AniLibria), собирает спеку эвристиками | 0, офлайн |
| 2. Перебор вариантов | пробует альтернативные селекторы и параметры, проверяет результат | 0 |
| 3. ИИ-помощь (опционально) | если 1–2 не справились: запрос к модели **с ключом пользователя** | по желанию |

Ключевое: ступени 1–2 покрывают большинство русских аниме-сайтов, потому что они на DLE
и WordPress. Это проверено на практике: детерминированный разбор дал 11/13 проверок,
свободная генерация кода моделью — 2/12.

## Компоненты

```
┌──────────────────────────── Takami (Android) ────────────────────────────┐
│  UI (Compose)                                                            │
│   ├── Библиотека, каталог, плеер, читалка — как в Tadami                  │
│   ├── «Добавить источник по ссылке»  ← новая точка входа                  │
│   └── Экран источника: имя, иконка, версия, настройки, «Проверить»        │
│                                                                          │
│  SourceRegistry                                                          │
│   ├── ApkSourceProvider      — существующие APK-расширения (как есть)     │
│   └── VirtualSourceProvider  — источники, созданные в приложении          │
│         (оба отдают один и тот же интерфейс AnimeSource)                  │
│                                                                          │
│  SpecEngine   — интерпретатор спеки                                      │
│   ├── HTTP/JSON клиент, шаблоны URL, пагинация                             │
│   ├── DOM-селекторы (jsoup) + аварийные текстовые границы                  │
│   ├── Фильтры path|query, сортировки                                      │
│   ├── Медиа: m3u8/mp4, iframe → цепочка плееров, качества                 │
│   ├── Cookie-сессия, WebView-логин, Cloudflare-фолбэк                     │
│   └── JS-хук (Rhino) для сайтов, где нужен код                            │
│                                                                          │
│  Forge (генератор)                                                       │
│   ├── EngineDetector  — DLE / WordPress / JSON / неизвестный              │
│   ├── SpecBuilder     — каталог, детали, серии, плеер, фильтры            │
│   ├── SelfCheck       — «стенд внутри приложения»                         │
│   └── Learner         — веса селекторов по хосту                          │
│                                                                          │
│  Локальное хранилище: site_profiles (JSON + веса), кэш спек, отчёты       │
└──────────────────────────────────────────────────────────────────────────┘
```

Шов с апстримом один: менеджер источников получает список из двух провайдеров вместо
одного. `sourceId` APK-расширений не меняется — иначе рушится библиотека.

## Поток «пользователь вставил ссылку»

1. **Разбор**: главная страница → определение движка (DLE по `/engine/`, WordPress по
   `/wp-content/`, JSON по ответу API, иначе общий HTML).
2. **Сборка спеки**: каталог, пагинация, карточка, детали, серии, плеер, фильтры — из
   вёрстки, не из догадок.
3. **Самопроверка** (тот же набор, что на компьютерном стенде): каталог ≥ 10 карточек,
   вторая страница отличается, детали дают название и постер, серии непустые, порядок
   правильный, медиа-ссылка действительно отдаёт поток, фильтры меняют выдачу.
4. **Починка**: проваленные шаги → перебор альтернатив (другие селекторы, другой
   параметр пагинации, POST вместо GET), запись того, что сработало.
5. **Регистрация**: источник попадает в общий список рядом с APK-расширениями, с иконкой
   из favicon/og:image, версией спеки и кнопкой «Проверить снова».
6. **Обучение**: результат и выбранные альтернативы пишутся в `site_profiles[host]`.
   При регрессии — откат к предыдущему профилю.

## Профиль сайта

Профиль — не код и не данные сайта, а **набор гипотез с весами**:

```json
{
  "host": "example-anime.org",
  "engine": "dle",
  "selectors": {
    "card": [{"q": "article a[href]", "w": 0.9}, {"q": ".shortstory a", "w": 0.4}],
    "desc": [{"q": ".fdesc.full-text", "w": 1.0}, {"q": "#dle-content", "w": 0.3}]
  },
  "pagination": {"kind": "path", "template": "page/{n}/", "w": 1.0},
  "media": {"kind": "iframe+mp4", "label_re": "\\[([^\\]]+)\\]\\s*(https?://\\S+\\.mp4)", "w": 0.8},
  "checks": {"catalog": 1, "details": 1, "search": 0},
  "fails": 0,
  "updated": "2026-11-01"
}
```

Обучение = пересчёт весов по результатам проверок. Ничего, что описывает конкретный
сайт, в APK не уезжает: профили создаются и живут на устройстве пользователя.

## Мастер создания источника

Семь экранов, каждый — подтверждение. Всё, что можно проверить машиной, проверяется
машиной; человек подтверждает только субъективное.

| № | Экран | Автоматически | Спрашиваем человека |
|---|---|---|---|
| 1 | Как источник выглядит | имя из `og:site_name`/`title`, иконка из `og:image`/favicon | «так пойдёт?» + правка |
| 2 | NSFW | плотность 18+ в выборке | тумблер, по умолчанию **выключен** |
| 3 | Популярное | лента, постеры (200 + `image/*`), плеер отдаёт `mp4/m3u8` | пять галочек |
| 4 | Недавние | сравнение с популярными по набору URL и заголовков | «отличается от популярных» (предзаполнено) |
| 5 | Фильтры | применить фильтр, сравнить выдачу до/после | «фильтр работает» |
| 6 | Поиск | искать реальный тайтл из каталога | «поиск нашёл» |
| 7 | Готово | сводка проверок | «сохранить» / «сохранить как черновик» |

Галочки на третьем экране: лента листается · картинки грузятся · видео есть · выбор
качества есть · выбор озвучки есть.

Правила: предпросмотр видео — 5–8 секунд без звука или первый кадр, иначе мастер съедает
трафик; если хоть одна галочка не стоит, источник сохраняется как **черновик** с пометкой
в списке; экраны входа через WebView и прохождения Cloudflare показываются только когда
нужны.

## Слепки сайта

Чтобы не разведывать заново, приложение хранит локальный слепок: главная, 1–2 страницы
каталога, страница тайтла, ответ плеера. Перед сохранением вырезаются cookie,
`Authorization`, CSRF-токены, скрипты и реклама. 200–400 КБ на сайт, лимит ~50 МБ,
старые вытесняются. Слепок не покидает устройство.

Перегенерация в настройках источника: **из слепка** (офлайн, быстро, ловит ошибки логики)
или **обновить слепок** (свежая выборка, ловит изменения сайта). Фоновая проверка считает
структурный хеш каркаса — набор селекторов и шаблонов; изменился — уведомление
«сайт изменился, перегенерировать?».

## Открытые вопросы

- Нужен ли JS-хук сразу (он нужен 3 спекам из 30) или на этапе 4?
- Слепок — в БД или файлами? Влияет на размер и вытеснение.
- Сколько галочек минимум, чтобы сохранять не черновик, а готовый источник?
- Сайт требует вход: предлагать сразу или после провала первой проверки?

## Этапы

| Этап | Содержание | Проверка |
|---|---|---|
| 0 | Форк, ребренд, оформление репозитория | репозиторий и README |
| 1 | Спека v1 + интерпретатор (каталог, детали, серии, медиа) | 3 сайта в тестовой обвязке без UI |
| 2 | Генератор (детектор движка + сборщик) + самопроверка | 3 сайта генерируются из ссылки |
| 3 | `VirtualSourceProvider` + экран «добавить по ссылке» | источник виден в списке как обычный |
| 4 | Cookie/WebView-логин, JS-хук, фильтры | сайт с авторизацией и сайт с JS |
| 5 | Профили с весами и откатом | намеренно испорченный селектор чинится сам |
| 6 | Переименование пакета, собственные релизы | сборка, ключ подписи, миграция |

## Риски

1. **Сайты без явного движка** — ступень 1 даст низкую уверенность. Нужен честный отказ
   («не смог, попробовать через ИИ»), а не молчаливо пустой источник.
2. **Cloudflare и капча** — только WebView-сессия; без неё часть сайтов недоступна.
3. **Батарея и трафик** при самопроверке — проверять на одном тайтле, медиа не скачивать,
   только первые байты.
4. **Смена `applicationId`** — ломает обновление поверх Tadami. Делать только вместе с
   миграцией библиотеки или не делать вовсе.
